### Confirmed-fake/schema-only areas (unchanged from prior audit, re-verified this session)
- **DKIM** — `services/worker/src/verifier/DkimVerifier.ts:67-110` explicitly simulates verification (`signature.length > 32` check), not real cryptography. This corrupts DMARC alignment results downstream.
- **Geolocation** — only `NullGeoProvider`, always returns `null`. No MaxMind/ip-api dependency anywhere.
- **Blockchain anchoring** — `BlockchainAnchor` Prisma model + one `PENDING` demo seed row only. No client/SDK code, `infra/blockchain/` is empty.
- **P1/P2/P3** — does not exist anywhere in the codebase. Real vocabulary is `Priority` enum (`LOW|MEDIUM|HIGH|CRITICAL`, on `Case`/`RiskAssessment.riskLevel`) and a separate `AlertSeverity` (`INFO|LOW|MEDIUM|HIGH|CRITICAL`, on `Alert` only).

## 8. Security concerns (informational — no changes made)

- DKIM's simulated verification can produce a false DMARC PASS, which is a correctness/security-messaging risk if ever presented to an analyst as trustworthy (already flagged in `CIPERSCOPE_UI_ARCHITECTURE.md`, and Step 11 of the master prompt explicitly requires the UI to disclose this honestly rather than fix the crypto in this phase).
- Case↔Email cross-organization linkage is not rejected at the DB layer (self-documented gap in `packages/database/src/case.integration.test.ts`) — relies on application-layer enforcement in `case.routes.ts`, which does appear to check `organizationId` consistently in the routes inspected, but this is a standing architectural note, not a new finding.
- No other new security issues found this session; RBAC enforcement itself (`rbac.ts`) was not modified and remains real/strict.

## 9. Recommended implementation order

1. **`packages/types`** — application-facing types only (not raw Prisma re-exports), covering the real API responses already verified above. Foundation for everything else.
2. **`packages/api-client`** — typed wrapper over the *actual* routes inventoried in §3 (including both the `case.routes.ts`-nested and the thin standalone `evidence`/`investigation` reads — clearly distinguished, not merged into fake unified endpoints).
3. **P1/P2/P3 priority model** — a presentation-layer mapping (`CRITICAL→P1`, `HIGH→P2`, `MEDIUM+LOW→P3`) documented and implemented consistently in `packages/types`, surfaced through the API client, not a new backend field (matches the existing internal audit's already-resolved decision in `CIPERSCOPE_UI_ARCHITECTURE.md:129`, which this phase should reuse rather than re-litigate — no scientific-validation claims).
4. **Dashboard upgrade** using real `/overview` data plus the priority mapping (fix the `recentAlerts`-is-actually-cases naming while there).
5. **One complete vertical slice: Email Forensics view** — this endpoint surface is already the most complete real-data area (headers/MIME/SPF/DKIM/DMARC/URLs/attachments/geolocation/ai-analysis/threat-indicators all real reads today), making it the lowest-risk, highest-payoff first placeholder replacement, and it directly satisfies Step 7/8 of the master prompt.
6. **Investigation Workspace upgrade** — wire the already-built-but-unused `/workspace` and `/decisions` endpoints into `InvestigationWorkspace.tsx` (currently only `/intelligence` is used) before touching any other placeholder page — this is backend work already done, purely a frontend integration gap.
7. Remaining placeholders (Evidence Vault, Timeline, Reports, Audit Log, etc.) — after the above, in the order the master prompt specifies, each as its own reviewed increment.
8. `packages/ui` component library — build incrementally *as needed* by the above slices, not upfront as a speculative library (avoids inventing components nothing consumes yet).
